# BIM USDT-TRC20 企业级钱包建设方案书

> 版本：V1.0  
> 日期：2026-07-11  
> 适用系统：BIM Flutter 客户端、TP8 业务端、后台管理系统、Gateway、Redis、MySQL、现有钱包与 OTC 系统  
> 文档性质：架构与实施评审稿，不代表已完成生产部署

## 1. 建设目标

在 BIM 现有法币钱包和 OTC 系统之上增加独立的 USDT-TRC20 数字资产钱包，实现：

1. 每个用户分配唯一的 TRON/TRC20 充值地址。
2. 用户可以从外部钱包向 BIM 地址充值 USDT。
3. BIM 用户之间可以进行 USDT 站内转账。
4. 用户可以将 USDT 提现到外部 TRC20 地址。
5. 用户可以查询可用余额、冻结余额、充值、转账、提现和手续费明细。
6. 后台可以查看地址、链上交易、归集、提现审批、热钱包、资源、风险和对账情况。
7. 钱包服务支持幂等、审计、灾备、告警、密钥隔离和后续水平扩容。

本方案不把 USDT 余额存入现有人民币余额字段，不允许通过修改 `mr_user.money` 实现数字资产余额。

## 2. 产品边界

### 2.1 首期支持

- 资产：USDT。
- 网络：TRON，客户端显示 `TRC20`。
- 充值：外部地址向用户专属地址充值。
- 站内转账：BIM 用户之间账本转账，不产生链上交易。
- 提现：从平台热钱包向外部 TRON 地址发送 USDT。
- 充值归集：用户地址余额自动归集至平台归集钱包。
- 钱包账单、服务号通知、后台管理、风险审核和财务对账。

### 2.2 首期不支持

- 不支持用户导出私钥、助记词或直接控制平台托管地址。
- 不支持 TRX、TRC10 或任意未经后台上架的 Token。
- 不支持跨链兑换、闪兑、合约理财、质押和 DeFi。
- 不允许同一地址同时标记为 TRC20、ERC20 等多个网络。
- 不允许客户端直接访问 TRON 节点或持有签名密钥。
- 不允许业务 API 直接拼装和签名链上交易。

## 3. 核心原则

### 3.1 链上资产与平台账本分离

链上地址余额是资金存放状态，平台数字资产账本是用户所有权记录，两者必须每日和实时对账，但不能互相替代。

用户充值后，即使资金随后被归集到平台热钱包，用户账本中的 USDT 余额仍归属于该用户。用户站内转账只改变双方账本余额，不需要在两个用户充值地址之间发起链上转账。

### 3.2 双重记账

所有余额变化必须同时产生借方和贷方分录，任一业务订单的分录合计必须为零。禁止使用：

```sql
UPDATE wallet_asset_account SET available = available + ?
```

作为完整记账逻辑。余额快照只能由已落库账本分录在同一数据库事务内更新。

### 3.3 金额只使用整数最小单位

USDT-TRC20 通常使用 6 位精度。系统内部统一使用最小单位整数：

```text
1 USDT = 1,000,000 unit
```

数据库使用 `DECIMAL(36,0)` 或无符号大整数可表达的字符串，服务端使用任意精度整数运算。禁止使用 `float`、`double` 参与记账、手续费、余额和链上金额计算。

### 3.4 私钥隔离

TP8、Gateway、Flutter、后台管理页面和普通数据库均不得保存或读取明文私钥。链上签名必须由独立签名服务完成。

### 3.5 最终确认后入账

TRC20 是智能合约资产。广播成功不等于链上成功，区块打包也不等于最终成功。充值必须满足：

- 交易位于已固化区块；
- 合约执行结果成功；
- `Transfer` Event 的合约地址、发送方、接收方和金额解析正确；
- `txid + log_index` 未处理过。

满足以上条件后才能给用户增加可用余额。

## 4. 推荐总体架构

```text
Flutter 客户端
      │ HTTPS + device/timestamp/nonce/sign + 加密响应
      ▼
TP8 业务 API
      │
      ├── 用户、支付密码、风控、订单、服务号通知
      ├── 数字资产账本服务
      └── 钱包查询与提现申请
                    │ Redis Stream / 内部签名请求
                    ▼
          TRON Wallet Service（Go）
          ├── Address Service 地址生成
          ├── Chain Scanner 固化区块扫描
          ├── Deposit Processor 充值入账
          ├── Sweep Worker 自动归集
          ├── Withdrawal Worker 提现执行
          ├── Reconciliation 对账
          └── Node Adapter 节点适配
                    │ mTLS
                    ▼
          Signing Service / HSM / KMS
                    │
                    ▼
       自建 FullNode + SolidityNode
       + 第二节点提供商（只读灾备）

资金层：
用户充值地址 → 归集钱包 → 提现热钱包 → 外部地址
                         │
                         └→ 冷钱包/多签储备钱包
```

### 4.1 为什么使用独立 Go 钱包服务

- 链扫描、交易状态机、重试队列和并发归集不适合依附 PHP Web 请求生命周期。
- 可以与现有 Gateway 使用一致的 Go 运维体系，但必须作为独立进程和独立权限域。
- 后续支持多节点、分片扫描和主从选举时不需要重构 TP8。
- 签名服务可以只允许钱包服务访问，降低私钥暴露面。

### 4.2 服务职责边界

| 模块 | 负责 | 禁止负责 |
|---|---|---|
| Flutter | 展示地址、二维码、余额、订单状态和安全确认 | 不生成私钥、不签名、不自行判断充值到账 |
| TP8 API | 鉴权、支付密码、风控、账本、业务订单、后台 | 不保存明文私钥、不直接广播交易 |
| Wallet Service | 地址派生、扫描、归集、提现编排、对账 | 不处理用户登录、不直接改法币余额 |
| Signing Service | 密钥解密、交易签名、签名策略 | 不连接公网、不读取用户业务数据 |
| TRON Node | 广播、区块、交易和 Event 数据 | 不作为平台账本 |

## 5. 地址分配方案

### 5.1 推荐方案：HD 分层确定性地址

使用 BIP39/BIP32/BIP44 兼容的 TRON HD 地址派生体系，为每个用户派生唯一地址。主种子只存在于 HSM/KMS 或离线密钥系统中。

建议路径示例：

```text
m/44'/195'/account'/0/address_index
```

其中 TRON coin type 为 195。实际生产路径需要在实施前固定并写入密钥恢复手册，投入使用后不得随意更改。

数据库只保存：

- 用户 ID；
- 地址；
- 地址索引；
- 派生路径；
- 地址状态；
- 创建时间；
- 可选的加密公钥信息。

数据库不保存主种子、助记词和明文私钥。

### 5.2 地址分配时机

推荐“首次打开 USDT 钱包时分配”，而不是注册时立即创建，原因：

- 避免为从未使用钱包的用户生成大量地址记录；
- 减少密钥派生和地址监控规模；
- 地址分配失败不会影响注册和 IM 主流程。

接口必须幂等：同一用户、同一资产、同一网络只能有一个当前充值地址。

### 5.3 地址格式和网络识别

- 客户端展示 TRON Base58Check 地址，通常以 `T` 开头。
- 服务端必须完成 Base58Check 校验并转换为 Hex 地址复核。
- USDT 合约地址必须来自后台受控资产配置，不接受客户端提交合约地址。
- 主网和测试网数据库、节点、密钥、地址和配置必须完全隔离。

### 5.4 地址激活

新生成地址在链上可能尚未激活。TRON 官方文档说明，账户激活会产生 TRX 和资源成本。平台不应在地址生成时批量激活所有地址。

推荐策略：

1. 地址可以先展示并接收 USDT。
2. 检测到充值后，归集任务判断账户是否激活及是否具有足够 TRX/Energy。
3. 由资源钱包按策略为需要归集的地址补充最小 TRX 或委托资源。
4. 归集完成后回收或停止继续补充资源。

资源费用必须通过测试网和主网实测动态估算，不能在代码中写死固定 TRX 手续费。

## 6. 充值流程

### 6.1 用户流程

```text
钱包 → USDT → 充值 → TRC20
```

页面展示：

- USDT-TRC20；
- 用户专属地址；
- 二维码；
- 复制地址；
- 最低充值金额；
- 预计到账确认规则；
- “仅向此地址充值 USDT-TRC20”的明确提示；
- 充值记录及状态。

禁止展示私钥、助记词、内部地址索引或节点信息。

### 6.2 链扫描流程

1. Scanner 从上次已处理的固化区块高度继续扫描。
2. 只解析配置中的官方 USDT TRC20 合约 `Transfer` Event。
3. 将 `to` 地址与地址表匹配。
4. 将原始事件写入链事件表，唯一键为：

```text
network + contract_address + txid + log_index
```

5. 验证交易合约执行成功且已固化。
6. 检查金额是否达到后台最低充值金额。
7. 在数据库事务内创建充值订单、双重账本分录并更新余额快照。
8. 发送“USDT 充值到账”服务号通知。
9. 将该地址加入归集队列。

### 6.3 充值状态

```text
detected       已检测
confirming     确认中
credited       已入账
below_minimum  低于最低充值
risk_hold      风控审核
reversed       冲正（只允许财务补偿流程）
```

正常情况下，已经按固化区块确认的充值不能删除。后台只能追加冲正分录，不能直接修改原充值金额。

### 6.4 漏扫和重扫

- 保存最后扫描高度和最后固化高度。
- 每轮扫描保留安全回看窗口，例如重新检查最近 N 个固化区块。
- 事件表唯一键保证重复扫描不会重复入账。
- 支持按区块范围、txid、地址人工重扫。
- 重扫操作必须记录管理员、原因、范围和 trace_id。

## 7. 自动归集

### 7.1 归集目的

用户充值地址不应长期保存大量资产。充值入账后，将余额归集到平台归集钱包，以便统一资金管理和提现。

### 7.2 归集触发条件

- 地址已存在可归集 USDT；
- 充值已经最终确认；
- 地址没有进行中的归集交易；
- 金额达到归集阈值，或达到定时归集窗口；
- 资源估算成功；
- 风控没有冻结该地址；
- 热/归集钱包策略允许执行。

### 7.3 Energy 与 TRX 策略

TRC20 转账是智能合约调用，会消耗 Energy 和 Bandwidth。推荐顺序：

1. 平台质押 TRX 获取资源；
2. 对充值地址委托 Energy；
3. 必要时由资源钱包补充受限额度 TRX；
4. 归集后停止或回收资源授权。

系统必须记录每笔归集的 Energy、Bandwidth、实际 TRX 成本和失败原因，后台按日统计单笔平均成本。

### 7.4 归集状态机

```text
queued → resource_preparing → signing → broadcasted
       → confirming → success
       → retry_wait / manual_review / failed
```

广播返回成功只进入 `broadcasted`，不能直接标记 `success`。

## 8. 用户站内转账

### 8.1 定义

两个 BIM 用户之间的 USDT 转账优先使用平台内部账本，不发起 TRON 链上交易。

优点：

- 实时到账；
- 不消耗 Energy/TRX；
- 可应用支付密码、限额、风控和服务号通知；
- 不受链上拥堵影响。

### 8.2 收款人识别

支持：

- 用户名；
- BIM 用户二维码；
- 绑定的 BIM 用户 ID 内部映射；
- 可选：识别平台自有 TRC20 地址后转为站内转账。

客户端不得显示数据库 ID 或 IMUID。确认页必须展示对方昵称、`@用户名` 和脱敏头像，防止同名误转。

### 8.3 站内转账流程

1. 查询收款人并返回确认资料。
2. 输入金额和备注。
3. 风险预检：钱包状态、可用余额、单笔/日限额、收款人状态、设备风险。
4. 用户输入支付密码；高风险交易追加短信/邮箱验证码或人工审核。
5. 使用 `request_id` 做幂等控制。
6. 数据库事务中锁定付款方资产账户。
7. 创建转账订单和双重分录：付款方扣减、收款方增加。
8. 提交事务后发送支付服务号通知和实时钱包更新事件。

### 8.4 转账不可逆规则

站内转账一旦成功，不允许客户端撤回。确需退款必须创建反向退款订单和新账本分录，保留原订单完整审计链。

## 9. 链上提币

### 9.1 用户流程

```text
钱包 → USDT → 提币 → TRC20
```

用户填写或扫描外部地址，系统展示：

- 提币网络；
- 提币地址；
- 数量；
- 平台手续费；
- 实际到账数量；
- 最小提币数量；
- 预计处理时间；
- 风险警告。

提交时必须验证支付密码。根据风险等级追加验证码、冷静期或人工审核。

### 9.2 地址校验

- Base58Check 校验；
- Hex/Base58 双向转换一致性校验；
- 禁止向 USDT 合约地址、零地址、平台黑名单地址提币；
- 检测是否为平台用户地址，若是则提示改用免费站内转账；
- 首次地址或大额提币触发增强验证；
- 地址簿修改后设置可配置冷静期。

### 9.3 提币资金流程

1. 客户端提交 `request_id`、地址、金额、支付密码和安全验证码。
2. TP8 完成鉴权、签名校验、设备校验和风控。
3. 数据库事务锁定用户数字资产账户。
4. 将“提币金额 + 平台手续费”从可用余额转入冻结余额。
5. 创建提现订单和冻结账本分录。
6. 风控通过后写入提现队列。
7. Wallet Service 估算 Energy，构建交易。
8. Signing Service 按策略签名。
9. 广播并保存 txid。
10. SolidityNode 确认合约执行成功后，完成提现账本结算。
11. 如果广播前失败，可解冻；如果交易已广播，必须先确认链上最终结果，禁止直接退款。

### 9.4 提币状态机

```text
submitted       已提交
risk_review     风控审核
approved        审核通过
queued          等待执行
signing         签名中
broadcasted     已广播
confirming      链上确认中
success         已完成
rejected        已驳回并解冻
failed_retry    执行失败待重试
manual_review   人工处理
```

不得把网络超时直接解释为失败。未知结果必须进入 `manual_review` 或继续按 txid 查询。

### 9.5 手续费策略

后台支持：

- 固定 USDT 手续费；
- 最低提币金额；
- 每用户单笔、单日和每月限额；
- VIP/认证等级差异化限额；
- 平台承担链上 TRX 成本或折算为 USDT 手续费；
- 紧急暂停提币。

手续费配置必须带版本号。提现订单创建时固化当时的手续费配置，后续修改不能改变已提交订单。

## 10. 热钱包、冷钱包和密钥体系

### 10.1 钱包分层

| 钱包 | 用途 | 建议余额 |
|---|---|---|
| 用户充值地址 | 接收用户充值，短期停留 | 尽量低 |
| 资源钱包 | TRX 质押、Energy 委托和地址激活 | 按日预算 |
| 归集钱包 | 接收充值归集 | 中等 |
| 提现热钱包 | 自动处理日常提现 | 仅保留预计 1-2 日额度 |
| 冷钱包/多签钱包 | 大部分平台储备 | 绝大部分资产 |

### 10.2 密钥管理等级

生产推荐优先级：

1. 专用 HSM；
2. 云 KMS/HSM，并验证支持 secp256k1 或使用安全封装；
3. 独立签名机 + 加密主种子 + 双人授权；
4. 禁止把私钥写入 `.env`、MySQL、Redis、日志、Docker 镜像或 Git 仓库。

### 10.3 签名服务安全规则

- 不提供“传入任意交易并签名”的通用接口。
- 只允许预定义 USDT 合约、网络、目标类型和额度范围。
- 验证调用方 mTLS 证书和短期服务令牌。
- 验证订单号、金额、目标地址和数据库审批结果。
- 单笔、大额、单日累计超过阈值时要求多签或人工批准。
- 每次签名生成不可篡改审计记录，但日志不得包含私钥。

## 11. 数据库设计

建议新增以下领域表，表名前缀沿用生产配置。

### 11.1 资产与网络配置

`wallet_chain_asset`

```text
id, appid, asset_code, network_code, contract_address,
decimals, deposit_enabled, withdraw_enabled,
min_deposit_units, min_withdraw_units, withdraw_fee_units,
confirm_policy, status, config_version, create_time, update_time
```

唯一键：`appid + asset_code + network_code`。

### 11.2 用户资产账户

`wallet_asset_account`

```text
id, appid, user_id, asset_code, network_code,
available_units, frozen_units, version, status,
create_time, update_time
```

唯一键：`appid + user_id + asset_code + network_code`。所有扣款使用行锁或乐观锁版本号。

### 11.3 地址表

`wallet_chain_address`

```text
id, appid, user_id, asset_code, network_code,
```

## 12. API 规划

所有用户 API 继续使用现有 `device + timestamp + nonce + sign + token` 安全请求规范，敏感响应按现有企业级密文方案返回。

### 12.1 用户接口

```text

wallet_asset_deposit_address   获取或分配充值地址
wallet_asset_deposit_list      充值记录
wallet_asset_transfer_preview  站内转账预检查
wallet_asset_transfer_create   创建站内转账
wallet_asset_withdraw_preview  提币预检查和手续费试算
wallet_asset_withdraw_create   创建提币申请
wallet_asset_withdraw_list     提币记录
wallet_asset_bill_list         数字资产账单
wallet_asset_order_detail      订单详情
wallet_asset_address_validate  提币地址验证
```

### 12.2 钱包内部接口

只开放在内网，通过 mTLS 和服务身份认证：

```text
internal/address/derive
internal/deposit/credit
internal/sweep/enqueue
internal/withdraw/claim
internal/withdraw/update
internal/sign/request
internal/reconcile/run
```

### 12.3 接口安全要求

- 金额使用字符串最小单位或十进制定点字符串。
- 客户端不提交 decimals、合约地址、手续费或实际到账金额作为可信参数。
- 所有写接口必须带 `request_id`。
- 同一 request_id 的参数哈希不一致时拒绝处理。
- 风险、余额、手续费和地址必须由服务端重新计算。
- 日志允许开发期记录业务字段，但永远禁止记录支付密码、验证码、私钥、助记词和完整签名密钥材料。

## 13. 后台管理

在现有钱包管理下增加“数字资产”菜单：

### 13.1 资产配置

- USDT 合约地址和 decimals；
- 充值、提币开关；
- 最低充值、最低提币和手续费；
- 用户等级限额；
- 归集阈值；
- 紧急暂停。

合约地址等关键配置修改必须双人复核，不能由单个管理员即时生效。

### 13.2 地址管理

- 用户、地址、派生索引和状态；
- 链上余额；
- 最近充值和归集；
- 资源状态；
- 风险冻结；
- 不展示私钥。

### 13.3 充值管理

- txid、区块、用户、地址、金额和确认状态；
- 重扫、补记和风险审核；
- 补记只能创建审计订单和账本分录，不能直接修改余额。

### 13.4 提币管理

- 自动、人工审核队列；
- 大额提币双人审批；
- txid 和链上状态；
- 驳回原因；
- 失败重试和人工处理；
- 禁止对已广播且状态未知的订单直接退款。

### 13.5 钱包与资源监控

- 热钱包 USDT 和 TRX 余额；
- Energy、Bandwidth、质押和委托；
- 待归集地址数量；
- 充值扫描高度差；
- 提现积压；
- 节点高度差；
- 签名服务健康状态。

## 14. 风控体系

### 14.1 用户风险

- 新设备登录后提币冷静期；
- 修改支付密码、安全手机号、邮箱或提币地址后的冷静期；
- 支付密码连续错误锁定；
- 单笔、单日、单月限额；
- 异常 IP、代理、设备指纹、登录地点变化；
- 高频小额拆分、短时间充值后全部提走；
- 多账户向同一外部地址提现；
- 黑名单地址和风险标签。

### 14.2 资金风险

- 热钱包余额上限；
- 单笔自动签名上限；
- 单日自动提现总额上限；
- 超限切换人工审批或多签；
- 充值到账后按风险等级设置可提等待期，但不能隐瞒冻结原因；
- 对账差异超过阈值自动暂停提现。

### 14.3 管理风险

- 管理员 RBAC 最小权限；
- 资产配置、放币、补账、大额审批分权；
- 关键操作双人复核；
- 管理操作全量审计；
- 后台不能查看私钥；
- 生产签名服务禁止通过后台浏览器直接调用。

## 15. 高可用与高并发

### 15.1 Scanner

- 多实例部署，但同一网络同一分片通过 Redis 租约或数据库租约选主。
- 游标更新和事件落库保持事务一致。
- 允许按地址哈希或区块区间分片，但首期建议单主扫描 + 热备。
- 节点异常时切换只读灾备节点，广播节点切换需独立控制。

### 15.2 队列

使用 Redis Stream 或可靠消息队列处理：

- 充值确认；
- 归集；
- 提现；
- 通知；
- 对账；
- 风险复核。

每个消费者必须有幂等键、重试次数、指数退避、死信队列和人工恢复入口。

### 15.3 数据库

- 资产账户按 `appid + user_id + asset + network` 唯一。
- 余额更新使用行锁和版本号。
- 账本表按时间或业务类型规划归档。
- 链事件表按区块高度或月份分区。
- 所有财务表禁止物理删除。

## 16. 对账与审计

### 16.1 三方对账

每天至少执行：

```text
用户资产负债总额
  = 热钱包资产
  + 归集钱包资产
  + 用户地址未归集资产
  + 冷钱包归属资产
  - 平台自有资产
  - 已广播待确认提现
```

同时核对：

- 链事件与充值订单；
- 充值订单与账本分录；
- 提现订单与冻结/扣款分录；
- 提现订单与链上 txid；
- 归集订单与地址余额变化；
- 手续费收入与链上 TRX 成本。

### 16.2 差异处理

- 小于阈值：告警并进入人工确认；
- 超过阈值：自动暂停提币和自动签名；
- 任何差异修复必须通过补偿订单和账本分录；
- 禁止直接改余额或删除原记录。

## 17. 告警与可观测性

关键指标：

- 固化区块扫描延迟；
- 节点高度差和响应延迟；
- 未处理充值数量；
- 归集失败率；
- 提现队列长度和处理时长；
- 热钱包 USDT/TRX 余额；
- Energy 使用率；
- 签名失败和拒绝次数；
- 账本不平衡次数；
- 对账差异；
- 同一 txid/log_index 重复处理拦截次数。

日志统一包含：`trace_id`、业务订单号、txid、用户 ID、网络、状态变化和耗时。日志中地址可以完整记录用于开发和审计，但生产后台展示应按权限脱敏。

## 21. 上线验收标准

### 21.1 财务正确性

- 任何业务订单分录合计为零；
- 重复扫描同一事件不会重复入账；
- 相同 request_id 不会重复转账或提币；
- 余额不足并发请求只能有一笔成功；
- 从账本分录可以重建余额快照；
- 链上资产与用户负债对账一致。

### 21.2 链上正确性

- 只识别配置中的 USDT 合约；
- 只在交易执行成功并固化后入账；
- Event 的 `txid + log_index` 全局唯一；
- 节点切换和区块重扫不会重复处理；
- 广播超时不会直接重新构造第二笔提现。

### 21.3 安全

- 代码、日志、数据库和环境变量中不存在明文私钥；
- 签名服务无法签署非白名单合约或超限交易；
- 大额提现需要双人审批或多签；
- 支付密码错误锁定、设备风险和冷静期有效；
- 后台关键操作全部有审计记录；
- 对账异常能自动暂停提币。

### 21.4 性能

- 充值扫描延迟处于配置阈值内；
- 站内转账在正常数据库负载下秒级完成；
- 提现队列可水平扩容且不会重复执行；
- 10 倍预估峰值下账本和幂等约束仍正确；
- 节点不可用时业务能进入明确等待状态，不丢单、不重复扣款。

## 22. 企业安全审核清单

上线前必须由研发、安全、财务和运维共同签字确认：

- [ ] 钱包托管与运营地区法律合规已经确认。
- [ ] USDT TRC20 合约地址由双人核验。
- [ ] 生产和测试网络、密钥、数据库完全隔离。
- [ ] 主种子已离线备份并完成恢复演练。
- [ ] TP8、客户端和数据库无明文私钥。
- [ ] 签名服务使用 mTLS、白名单和金额策略。
- [ ] 所有金额使用整数最小单位。
- [ ] 充值只在固化且执行成功后入账。
- [ ] 提现具备幂等、冻结、审批、广播和确认状态机。
- [ ] 广播结果未知时不会自动退款或重复广播。
- [ ] 双重账本通过并发和故障注入测试。
- [ ] 对账异常可以自动暂停提现。
- [ ] 热钱包限额和冷钱包补充流程已经演练。
- [ ] 管理员权限分离和双人审批已经启用。
- [ ] 用户端风险提示、手续费和到账金额准确。
- [ ] 服务号通知不会泄露完整敏感信息。
- [ ] 监控、告警、日志和应急联系人已经配置。

## 23. 关键决策建议

在进入开发前，需要最终确认以下决策：

1. BIM 是否作为托管钱包承担用户资产保管责任。
2. 是否自建 TRON FullNode/SolidityNode；建议生产自建主节点，第三方节点仅作灾备和数据交叉验证。
3. HSM、云 KMS 或独立签名机的选择。
4. 热钱包最大余额、单笔自动提现和每日自动提现上限。
5. 最低充值、最低提币和 USDT 手续费。
6. 新设备、修改安全信息后的提币冷静期。
7. 大额提现人工审核和多签阈值。
8. 用户充值地址是一人一地址长期使用，还是支持地址轮换；首期建议一人一地址，后续增加轮换能力。
9. OTC 成交所得 USDT 是否直接进入本数字资产账本；建议统一进入同一账本，避免形成第二套余额。
