# BIM 企业级接口明文/密文安全方案

> 版本：v1.0  
> 日期：2026-07-04  
> 范围：BIM 客户端、TP8 业务端、BIM Gateway、底层 IM 服务

## 1. 背景

当前客户端和业务端已经对用户端敏感接口做了业务层加密：

- 登录、注册、短信验证码、邮箱验证码：使用登录前 `secure_payload` 提交；登录成功响应使用 `secure_response=1` 返回 token。
- `im_connect`：使用登录态 `secure_payload` 提交，响应只返回 `data.secure_payload`。
- 私聊/群聊发送：`receiver_id`、`group_id`、`content_type`、正文、红包、转账、媒体字段都放入 `secure_payload`。
- 会话/历史/好友/群/在线/交易/回执接口：统一使用 `secure_response=1`，服务端返回 `data.secure_payload`。
- 聊天文件：使用 `secure_file` 上传，服务端解密后保存。
- Gateway：ticket 为 `bgt_` 开头不透明票据，claims/frame_key 存 Redis；长连接 frame 使用 `AES-256-GCM` envelope。

但审查发现还有接口会返回或提交明文敏感数据：

仍需后续 v2 强化的部分：

- 登录/注册前当前使用 `appid|appkey|空token` 派生的 v1 密钥，生产 v2 应升级为公钥握手 + AES-256-GCM。
- ACK 当前仍提交 `ticket`、`last_cursor`、`client_msg_nos` 明文字段；其中 ticket 为不透明值，cursor/client_msg_no 不包含消息正文。
- 旧第三方登录接口没有纳入 BIM 客户端用户端入口，交付时应关闭或迁移后再开放。

HTTPS/TLS 只能防公网链路窃听；如果用户在设备上安装抓包证书、Hook 网络库、读取本地日志，仍可能看到 HTTP 层明文。因此企业级方案必须同时做：

- 传输层 HTTPS/TLS。
- 应用层 `secure_payload` / `secure_response`。
- Gateway 帧级加密。
- 明文接口白名单。
- 旧接口禁用。

## 2. 安全目标

1. 用户聊天内容、附件 URL、红包金额、转账金额、交易单号、名片、引用消息、阅后即焚参数不能在抓包中明文出现。
2. `im_connect` 不再明文返回 IM token、route、stream ticket 详细声明。
3. 好友关系、群成员、群名称、禁言原因、在线用户列表等社交图谱数据默认密文返回。
4. 旧私信接口彻底禁用，不能绕过 Gateway 和新 IM 业务层。
5. 开发期允许日志打印完整明文，生产期默认脱敏。
6. 客户自部署没有 HTTPS 时可以继续 HTTP，但生产推荐强制 HTTPS；应用层加密不依赖 HTTPS。

## 3. 数据分级

| 等级 | 数据 | 是否允许明文提交 | 是否允许明文返回 |
| --- | --- | --- | --- |
| P0 公共数据 | App 基础信息、版本更新、公开帖子、公开应用列表、公开分类、验证码图片 | 允许 | 允许 |
| P1 协议元数据 | `appid`、`timestamp`、`nonce`、`device_flag`、`device_level`、`secure_response`、接口路径、分页参数 | 允许 | 允许 |
| P2 身份凭证 | `usertoken`、登录 token、IM token、Gateway ticket、session secret | 不建议明文，过渡期仅允许请求携带 `usertoken` | 禁止 |
| P3 社交图谱 | `receiver_id`、`group_id`、好友列表、群成员、在线列表、禁言状态、好友申请 | 目标禁止，过渡期允许部分路由 ID | 禁止 |
| P4 聊天内容 | 文本、图片 URL、语音 URL、视频 URL、文件 URL、表情、GIF、贴纸、名片、引用、@列表、阅后即焚 | 禁止 | 禁止 |
| P5 财务/交易 | 红包金额、转账金额、资产类型、交易单号、领取记录、余额流水 | 禁止 | 禁止 |
| P6 管理/审计 | 后台聊天记录、Webhook 原始 payload、队列失败原因、用户最近聊天对象 | 后台 HTTPS + 权限控制 | 后台 HTTPS + 权限控制 |

## 4. 统一加密协议

### 4.1 现有 v1 协议

当前客户端和业务端已经实现：

- 请求密文：`secure_payload`
- 请求算法：`AES-128-CBC`
- 请求 key：`md5(appid|appkey|usertoken).substring(0,16)`
- 请求 IV：`md5(device|client_msg_no|timestamp|nonce).substring(0,16)`
- 响应密文：`data.secure_payload`
- 响应 IV：`md5(device|response|timestamp|nonce).substring(0,16)`

短期可以继续沿用 v1，先把所有敏感接口纳入 `secure_payload` / `secure_response`。

### 4.2 企业 v2 协议

中期建议升级到 v2：

- 算法：`AES-256-GCM`
- 外层字段：`appid`、`sid`、`timestamp`、`nonce`、`kid`、`secure_payload`、`secure_payload_alg`、`secure_payload_version`、`sign`
- `sid` 是随机会话 ID，不暴露用户 ID。
- 登录成功后服务端下发 `sid` 和 `session_secret`，后续请求用 `sid` 找密钥。
- 登录/注册前使用服务端公钥做一次性密钥交换，避免密码明文出现在抓包里。
- `usertoken` 不再作为普通表单字段长期暴露。

推荐过渡：

1. 先补齐 v1。
2. 客户端和服务端同时支持 v1/v2。
3. 后台打开 `API_SECURE_STRICT=1` 后只允许 v2。

## 5. 接口分类方案

### 5.1 允许明文接口

这些接口可以保留普通 JSON，因为数据本身是公开或低敏：

- `get_app_info`
- `get_app_update_records`
- `get_image_verification_code`
- `app_category_list`
- `app_category_children_list`
- `get_apps_list`
- `get_apps_information`
- 公开帖子列表、公开帖子详情、公开评论列表，前提是不返回用户隐私字段。

限制：

- 不能返回 `usertoken`、手机号、邮箱、余额、IM UID、Gateway ticket。
- 如果接口因为登录态返回个性化字段，个性化部分必须移入密文。

### 5.2 账号类接口

必须加密提交：

- `login`：`username`、`password`、`captcha`
- `mobile_login`：`mobile`、`captcha`
- `register`：`username`、`password`、`mobile`、`email`、验证码、邀请码
- `retrieve_password`
- `change_password`
- `modify_user_email`
- `modify_user_phone`
- `automatic_login`

必须加密返回：

- `usertoken`
- 用户 ID、用户名、昵称、头像以外的自有资料
- 余额、积分、VIP、绑定邮箱/手机号
- IM 连接配置

建议：

- 登录成功响应改成 `secure_response=1`。
- 外层只保留 `code`、`msg`、`timestamp`。
- `data` 内只返回 `secure_payload`。

### 5.3 `im_connect`

当前状态：

- 请求必须带 `secure_payload` 和 `secure_response=1`，并参与签名。
- 原始响应只返回 `data.secure_payload`。
- 解密后才包含 `uid`、`token`、`route`、`online_status`、Gateway stream 信息。
- Gateway `ticket` 是 `bgt_` 开头的不透明票据，不能被 base64 解出 claims。
- Gateway `frame_key` 只在密文 `im_connect` 响应中出现。

目标规则：

- 请求必须带 `secure_response=1`，并参与签名。
- 响应必须走 `secureChatResponse()`。
- 用户端不再返回底层 IM token 和原始 route。
- 客户端不走底层 SDK 时，只返回 Gateway 需要的最小字段：
  - `route.https_stream_addr`
  - `stream.ticket`
  - `stream.frame_key`
  - `stream.frame_alg`
  - `stream.expire_in`
  - `stream.last_cursor`
  - `channel_type_person`
  - `channel_type_group`
  - `history_sync`
- `stream.ticket` 改成不透明票据，不能是可 base64 解码的明文 claims。
- `uid`、`device`、`route` 如客户端确实需要，只能放在密文 payload 内。

验收：

- 抓包 `https://blcold.cn/api/im_connect` 原始响应中不允许出现：
  - `token`
  - `route`
  - `websocket_addr`
  - `ws_addr`
  - `wss_addr`
  - `uid`
  - `online_status`
  - `ticket` 的可读 claims

### 5.4 会话和历史接口

当前已完成：

- `im_conversations`
- `im_person_messages`
- `im_group_messages`

要求：

- 必须带 `secure_response=1`。
- 不带 `secure_response=1` 直接拒绝。
- 原始响应只能出现 `data.secure_payload`。
- 抓包不允许出现 `content`、`payload`、`red_packet`、`transfer`、`media.url`、`file_url`、`voice_url`、`video_url`。

### 5.5 发送消息接口

当前基本达标：

- `im_person_send`
- `im_group_send`

已有规则：

- 聊天正文、金额、备注、媒体 URL、名片、@、引用、阅后即焚等字段必须放入 `secure_payload`。
- 明文提交 `content`、`money`、`remark`、`url` 等字段时拒绝。
- 上传文件必须使用 `secure_file`。
- 普通 `file` 字段拒绝。
- 成功响应只返回 `client_msg_no`、`message_id`、`send_ack`，不返回 payload。

已增强：

- `receiver_id`、`group_id`、`content_type` 已移入 `secure_payload`，避免社交图谱和消息类型暴露。
- 服务端不再从密文中移除 `receiver_id`、`group_id`、`content_type`。
- `client_msg_no` 继续作为外层随机幂等号，不能包含用户 ID、时间戳明文组合。

### 5.5.1 钱包服务号通知

扫码收款、扫码付款成功后，系统通过独立“支付通知”服务号下发 `wallet_notice`，不允许把收款和支付信息写进好友私聊。

安全规则：

- 服务号系统用户为 `__wallet_service_{appid}`，只用于发送钱包通知，不进入好友列表。
- `wallet_notice` 的订单号、金额、付款方、收款方、支付时间必须在消息 payload 密文内，抓包不得出现明文。
- 会话列表允许展示低敏摘要，例如 `[付款]付款成功`、`[收款]收款到账`；不在摘要里展示完整订单号。
- 客户端必须把“支付通知”会话设为只读，禁止用户向服务号发送普通聊天、红包、转账和通话。
- 服务端发送通知使用幂等 `client_msg_no=wallet-notice-md5(appid|order_no|target|scene)`，扫码确认接口重试不能重复产生同一条通知。
- 通知发送失败只记录服务端错误日志，不回滚已经成功的收付款事务。

### 5.6 好友接口

涉及接口：

- `im_friend_search`
- `im_friend_list`
- `im_friend_apply`
- `im_friend_handle`
- `im_friend_apply_list`
- `im_friend_status`
- `im_friend_delete`

必须加密提交：

- `keyword`
- `friend_id`
- `remark`
- `apply_id`
- `handle_msg`

必须加密返回：

- 搜索结果
- 好友列表
- 好友申请列表
- 好友关系状态
- 用户资料、头像、昵称、用户名、申请备注

过渡方案：

- 先要求 `secure_response=1`。
- 再把提交参数迁入 `secure_payload`。

### 5.7 群聊管理接口

涉及接口：

- `im_group_create`
- `im_group_update`
- `im_group_list`
- `im_group_members`
- `im_group_members_add`
- `im_group_members_remove`
- `im_group_member_mute`
- `im_group_member_unmute`
- `im_group_mute_status`
- `im_group_admin_set`
- `im_group_owner_transfer`
- `im_group_leave`
- `im_group_delete`

必须加密提交：

- `group_id`
- `name`
- `avatar`
- `notice`
- `member_ids`
- `member_id`
- `new_owner_id`
- `reason`
- `expire_seconds`

必须加密返回：

- 群列表
- 群成员列表
- 群资料
- 群禁言状态
- 管理员/群主信息
- 操作结果中的群资料快照

允许明文：

- 操作成功时只返回 `code=1,msg=success`，且不带业务数据。

### 5.8 红包、转账、回执、撤回

涉及接口：

- `im_person_red_packet_receive`
- `im_group_red_packet_receive`
- `im_person_transfer_receive`
- `im_message_read_receipts`
- `im_message_receipt_status`
- `im_message_recall`
- `im_burn_after_read`
- `im_message_delete`
- `im_person_conversation_delete`
- `im_group_conversation_delete`
- `im_chat_records_clear_all`

必须加密提交：

- `red_packet_id`
- `transfer_id`
- `target_client_msg_no`
- `receipts`，格式为 `[{"target_client_msg_no":"...","message_seq":123}]`
- `client_msg_no`
- `message_seq`
- `receiver_id`
- `group_id`

必须加密返回：

- 回执状态
- 已读人数
- 红包领取状态
- 转账领取状态
- 任何包含交易单号、金额、接收人、消息号的数据

允许明文：

- 操作成功且无业务数据时，返回 `code=1,msg=success`。
- 发送 ACK 类响应如果只含 `client_msg_no`、`message_id`、`queued`、`duplicate`，可短期明文；严格模式下也应加密。

### 5.9 在线列表

涉及接口：

- `im_online_users`

要求：

- 用户端原则上不应获取全量在线列表。
- 如果用于“当前在线好友”，只返回当前用户好友范围内的数据。
- 必须 `secure_response=1`。
- 后台全量在线列表必须后台权限控制，不开放给普通用户端。

### 5.10 旧私信接口

高风险接口：

- `send_message`
- `get_message_list`
- `get_chat_log`

处理规则：

- 用户端直接返回 `410` 或业务错误：`旧私信接口已停用`。
- 不再写旧私信表。
- 不再返回旧聊天记录。
- 文档、客户端、后台入口全部移除旧调用。
- 数据库旧表可迁移后归档，不能作为新业务读取来源。

## 6. Gateway 安全方案

### 6.1 当前问题

Gateway 使用 HTTPS 长连接，外层是 TLS，但帧内是 JSON：

```json
{
  "type": "message",
  "payload": {"content":"hello"}
}
```

在普通公网中 HTTPS 是安全的；但在安装证书抓包、Root/Hook、调试环境中，HTTP 层仍可看到 payload。

### 6.2 目标方案

Gateway 帧也做应用层加密：

```json
{
  "frame_id": "1783163091375-0",
  "type": "message",
  "cursor": "1783163091375-0",
  "secure_payload_alg": "AES-256-GCM",
  "secure_payload_version": "2",
  "secure_payload": "base64..."
}
```

密文内包含：

- `uid`
- `channel_id`
- `channel_type`
- `client_msg_no`
- `message_id`
- `message_seq`
- `payload`
- `timestamp`

### 6.3 Gateway ticket

当前 HMAC ticket 如果是 `base64.claims.signature`，claims 可被解码看到 `uid`、`device`。

目标：

- 改为不透明 ticket。
- ticket 本身是随机字符串。
- ticket claims 存 Redis，TTL 与票据有效期一致。
- Gateway 只通过 Redis 查 claims。
- 支持单次使用，防重放。

### 6.4 ACK

ACK 请求短期可以保留明文：

- `ticket`
- `last_cursor`
- `client_msg_nos`

严格模式：

- `ticket` 使用不透明票据。
- `client_msg_nos` 移入 `secure_payload`。
- 外层只留 `ticket` 和 `secure_payload`。

## 7. 客户端改造方案

### 7.1 ApiClient

新增能力：

- `secureImPost()`：敏感接口统一加密提交。
- `secureImPost(..., secureResponse: true)`：敏感接口统一密文返回。
- `connectIm()` 改为 `secureResponse=true`。
- 好友/群聊/交易/回执接口全部支持密文提交和密文返回。

### 7.2 日志

当前客户端 `_safeLogParams()` 会隐藏 `usertoken`、`sign`、`secure_payload`、`money` 等字段。

开发期你要求日志显示所有数据，可以加配置：

```dart
AppConfig.debugFullApiLog = true
```

规则：

- 开发包：打印请求参数、响应明文、解密后的 payload。
- 生产包：默认脱敏，禁止打印 token、密码、金额、聊天内容、文件 URL、session secret。

### 7.3 本地缓存

本地 MMKV 已经做加密目录和密钥处理，后续还要确保：

- 缓存里不保存原始 token 明文。
- Gateway ticket 只保存在内存，不落盘。
- 聊天消息本地可以明文缓存，但 MMKV 必须加密；生产期可选二次消息体加密。

## 8. 服务端改造方案

### 8.1 公共方法

在 TP8 业务端增加统一方法：

- `requireSecureResponse()`
- `secureJson($data)`
- `secureInput($allowedPlainKeys = [])`
- `rejectPlainSensitiveFields($fields)`
- `decryptSecurePayload()`
- `encryptSecurePayload()`

避免每个接口自己写加密逻辑。

### 8.2 配置

`.env` 建议：

```ini
; 接口应用层加密开关
API_PAYLOAD_CRYPTO_ENABLED=true

; strict=1 时敏感接口不接受明文提交/返回
API_PAYLOAD_STRICT=false

; 开发期是否允许客户端/服务端日志打印完整明文
API_DEBUG_FULL_PAYLOAD_LOG=true

; 生产期是否强制 HTTPS
API_REQUIRE_HTTPS=false

; Gateway 票据是否使用不透明 Redis ticket
BIM_GATEWAY_OPAQUE_TICKET=true

; Gateway stream 帧是否应用层加密
BIM_GATEWAY_FRAME_CRYPTO=true
```

说明：

- 现在还在开发调试，`API_DEBUG_FULL_PAYLOAD_LOG=true` 可以打开。
- 发布生产前必须改成 `false`。
- 客户没有 HTTPS 时，`API_REQUIRE_HTTPS=false` 可以运行，但应用层加密仍然有效。

### 8.3 兼容期

建议设置三种模式：

| 模式 | 用途 | 行为 |
| --- | --- | --- |
| `off` | 本地联调 | 不强制应用层加密 |
| `compat` | 过渡 | 敏感接口优先密文，发现明文打日志告警 |
| `strict` | 生产 | 敏感接口明文提交/明文返回直接拒绝 |

本项目建议直接进入 `strict`，因为还没发布，不需要兼容旧客户端。

## 9. 验收清单

### 9.1 抓包验收

必须抓包检查：

- `im_connect`
- `im_conversations`
- `im_person_messages`
- `im_group_messages`
- `im_person_send`
- `im_group_send`
- `im_friend_list`
- `im_friend_search`
- `im_group_members`
- `im_person_red_packet_receive`
- `im_person_transfer_receive`
- Gateway `/api/sync/open`

抓包原文禁止出现：

- 聊天正文
- 图片/语音/视频/文件 URL
- 红包金额
- 转账金额
- 交易单号
- 收付款订单号和钱包服务号 payload 明文
- 用户 token
- IM token
- Gateway claims
- 好友列表
- 群成员列表
- 在线用户列表

### 9.2 自动化测试

需要写测试脚本：

1. 明文 `content` 调 `im_person_send`，必须失败。
2. 明文 `money` 调 `im_group_send`，必须失败。
3. 不带 `secure_response=1` 调历史消息，必须失败。
4. 调 `im_connect`，原始响应只能看到 `secure_payload`。
5. 调好友列表，原始响应只能看到 `secure_payload`。
6. 调群成员，原始响应只能看到 `secure_payload`。
7. Gateway stream 收消息，帧内不能出现 `payload.content` 明文。
8. 旧 `send_message` 返回停用错误。

## 10. 执行顺序

### 第一阶段：已完成

1. `im_connect` 必须 `secure_payload` + `secure_response=1`。
2. 客户端 `connectIm()` 改成安全提交和密文响应。
3. 登录接口不再返回 Gateway ticket；IM 连接材料统一由密文 `im_connect` 下发。
4. 旧私信接口未在用户端调用，服务端扫描未发现 `send_message/get_message_list/get_chat_log` 旧入口。
5. 好友列表、群列表、群成员、在线列表改成密文提交/密文响应。

### 第二阶段：已完成

1. 好友申请、好友处理、群创建、群管理、回执、撤回、删除、红包领取、转账领取全部走 `secure_payload` 提交。
2. `receiver_id`、`group_id`、`content_type` 等字段已移入密文。
3. 客户端 IM 业务动作已删除普通签名分支，统一走安全提交。

### 第三阶段：已完成

1. Gateway ticket 改不透明 Redis ticket。
2. Gateway stream 帧加密。
3. 客户端 Gateway 解帧后再写入本地缓存。
4. ACK 保留不透明 ticket + cursor；后续 v2 再把 `client_msg_nos` 移入密文。

### 第四阶段：后续增强

1. 登录/注册前使用公钥握手。
2. 登录后使用 `sid + session_secret`。
3. AES-256-GCM 替换 AES-128-CBC。
4. 服务端开启 strict。

## 11. 当前结论

当前已经落地：

- 登录、注册、验证码、IM 连接、IM 发送、会话、历史、好友、群管理、在线、红包/转账领取、回执都已纳入应用层加密规则。
- `im_connect` 原始响应只暴露 `data.secure_payload`。
- 好友/群管理/在线/交易领取/回执类接口已密文返回。
- 发送消息的社交图谱字段已迁入 `secure_payload`。
- Gateway ticket 已不透明化。
- Gateway stream payload 已做 `AES-256-GCM` 帧级加密。
- 服务端扫描未发现用户端仍调用的旧私信入口。

剩余 v2 增强：

- 登录/注册前改为服务端公钥握手，替换当前空 token v1 密钥。
- 登录后使用 `sid + session_secret`，减少外层长期携带 `usertoken`。
- ACK 的 `client_msg_nos` 可继续移入密文 payload。
